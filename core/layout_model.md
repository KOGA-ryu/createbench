# File: core/layout_model.py

## Purpose

Represents the entire UI layout as a deterministic, hierarchical tree structure. Acts as the single source of truth for all UI structure and properties.

## Responsibilities

* store and manage all UI nodes
* maintain parent-child relationships
* preserve ordering of children
* provide traversal and lookup of nodes
* allow creation, deletion, and modification of nodes
* provide export-ready structured data
* own the synthetic root container for the layout tree
* manage type-based ID counters for deterministic node creation

## Inputs

* node creation requests (from canvas or templates)
* property updates (from inspector)
* structural updates (add/remove/reparent nodes)

## Outputs

* full layout tree
* node references for selection and rendering
* serialized structure for export

## Internal Logic

* maintains a tree of nodes
* requires a synthetic internal root with id `root`
* allows many top-level children under the synthetic root
* maintains type-based counters for ID generation (for example `button_1`, `sidebar_2`)

* each node contains:

  * id (unique identifier)
  * type (node type)
  * name (optional)
  * properties (dict of key/value pairs)
  * parent_id (parent node reference by id)
  * children (ordered list)

* supports:

  * add_node(parent_id, node)
  * remove_node(node_id)
  * update_node(node_id, properties)
  * get_node(node_id)
  * traverse()
  * reorder_node(node_id, index)
  * move_before(node_id, sibling_id)
  * move_after(node_id, sibling_id)

## Root Definition

* synthetic root is required and always present
* synthetic root id is `root`
* synthetic root acts as the single internal container for the entire layout
* root cannot be deleted
* all export and traversal operations begin from the root
* top-level user nodes are children of the synthetic root

## ID Strategy

* IDs are generated by `layout_model`
* IDs are type-based and deterministic within a session
* format is `<type>_<n>`
* separate counters are maintained per node type
* duplicate IDs must be rejected

## Ordering Rules

* child order is authoritative for structure and visual layering
* tree order is visual order
* supports append
* supports insert at index
* supports move before sibling
* supports move after sibling

## Dependencies

* node.py (node structure definition)

## Constraints

* must NOT contain UI logic
* must NOT perform validation (handled by checklist system)
* must NOT depend on Qt or rendering logic
* must preserve strict ordering of children
* must keep a deterministic tree shape and traversal order

## Edge Cases

* removing a node with children must cascade delete the entire subtree
* duplicate IDs must be prevented
* orphan nodes (must not exist)
* circular references (must not occur)
* root deletion must be blocked
* reordering within the same parent must preserve stable ordering

## Export Behavior

* produces a complete representation of the layout
* includes all nodes and properties
* includes default values where properties are missing
* output must be deterministic and consistent
* supports explicit-only serialization mode
* supports fully-expanded serialization mode with defaults included

## First-Class Node Types

* `document`
* `container`
* `vertical`
* `horizontal`
* `split`
* `sidebar`
* `toolbar`
* `main`
* `panel`
* `button`
* `text`
* `input`
* `list`

## Nesting Policy

* no hard cap on nesting depth
* checklist system may issue soft warnings for deeply nested structures

## Decisions Locked

* one required synthetic `root` container with many children beneath it
* deletion is cascade delete
* IDs are type-based and generated by `layout_model`
* tree order defines visual order
* serialization supports both explicit-only and fully-expanded modes
